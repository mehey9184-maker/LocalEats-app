## L3-N8U-T — Codex location-blocker and hosted Customer profile fix (2026-11-21)

Owner-supplied Codex read-only browser acceptance report **BLOCKED at real geolocation**, not catalog: the signed-in Production Customer UI and bottom tabs loaded, but two device location requests returned `Error getting location (graceful fallback): Timeout expired`; screen showed `Location required`, **not** `Shops unavailable`. Codex did **not** establish any failed catalog URL or HTTP status, did **not** test out-of-area UI, menu or PWA, and performed no writes. Do NOT attribute this specific attempt to apex CORS (a separate independently verified bug fixed in API GitHub main, pending Vercel deployment).

**Source root cause of profile error:** current Customer `src/App.tsx` had `fetch('/api/profiles/<uid>')` and `src/lib/profileService.ts` used `POST /api/profiles` on the Vite SPA's own domain. Its catch-all `vercel.json` rewrite returns `index.html`, so `response.json()` parses `<!doctype...` or an empty HTML fallback. The actual authenticated server route is `GET/POST https://<configured exact VITE_LOCALEATS_API_URL>/api/v1/profiles/me`, with Firebase token verification, owner scope, and `PROFILE_WRITES_ENABLED=false` unless separately authorized.

**Draft-only fix in Customer PR #125:** `src/services/customerProfileApi.ts` builds the exact HTTPS server URL, sends the current Firebase account's Bearer token, demands JSON and matching returned `user_id`, treats only genuine JSON `PROFILE_NOT_FOUND` 404 as absence, refuses HTML/empty payload and privileged client fields. `src/App.tsx` reads through that API, falls back only to safe local Firebase Auth **display** metadata without role authority or a profile write, and removes old `/api/profiles` fallback. `src/lib/profileService.ts` no longer copies the same profile to direct Firestore, claims a fake offline success, or queues hidden retries while the **client VITE_PROFILE_WRITES_ENABLED** is OFF; server `PROFILE_WRITES_ENABLED` remains an independent gate. No Production profile data or account was changed.

**Real-location recovery:** Two competing `navigator.geolocation.getCurrentPosition` calls previously existed: the main `requestLocation` (15 seconds) and an extra 5-second unconditional startup call that could reset a successful location state. The duplicate was removed; main timeout is now **25 seconds** with useful location-service guidance and a real-device retry. No IP fallback, fake GPS, forced Tembisa coordinate, radius enlargement or pickup-write activation was added. **An OS/browser location service timeout is still a real-device blocker until tested**; this code change alone does not prove GPS works in Codex's cloud browser.
