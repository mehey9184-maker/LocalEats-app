## Boundary risks and proposed tests (not executed)
A rounded distance of 4.004 km displays 4.00 km and could pass a <=4 comparison although the raw distance is outside. Zero latitude/longitude are legitimate coordinates and must not be replaced by defaults. Missing/invalid GPS must never imply zero distance or pickup eligibility. Test fixture points with zero distance; 3.999, 4, 4.001, 4.004 km; swapped endpoints; antimeridian; poles/near antipodal; missing/null/NaN/Infinity/out-of-range; no rounding until presentation. Use deterministic numerical tolerances only for comparison of calculations, not to widen approved eligibility. Validate exact boundary policy against authoritative SQL and API, including potential floating-point rounding at mathematically exact 4 km. Check actual current hosted definition read-only before production conclusions. No live order needed. Origin vectors: blank explicit vs dev, HTTPS production root, HTTP local only, credential-bearing URL, non-root, query/hash, malformed, IPv4/IPv6 loopback, token absent, cancellation/aborted request. Auth and PWA tests must preserve role-specific semantics and current approved UI.

## ADR-011 — shared contracts before shared runtime packages (proposed)
Consolidate only proven identical behaviour. A shared contract + fixtures initially costs less and avoids coupling independent frontend deployments. Keep private authorization, pricing, pickup admission and database transactions authoritative on server/database. Do not introduce C++/WASM for small GPS calculations without measured CPU bottleneck, portability and safe fallback. No additional spend. Prioritize actual security gates over cosmetic deduplication. No runtime code, lockfile, database, deployment or flag changes in this review. Search results are partial; Rider repo and full call/deployment graph not reviewed.
