# LocalEats App Functionality Documentation

## Overview
LocalEats is a comprehensive food discovery and ordering application for local legendary Kota joints, featuring user authentication, profile setup, smart dispatch, and a seamless checkout experience with real-time live map tracking.

## Core Feature Implementation Details
- **Authentication & User Profiles**: Users can set up profiles, save delivery addresses, and manage preferences. Handled via Supabase Auth and `profiles` table.
- **Smart Dispatch Algorithm**: Dynamically assigns couriers (riders) to orders based on real-time geographical proximity to the store. Driven by a `calculateDistance` utility checking against live rider telemetry.
- **Order Tracking System**: UI represents strict tracking phases:
  - *Pending*: Default state.
  - *Cooking*: Order is being prepared.
  - *Ready*: Order is prepared and waiting for pickup.
  - *Rider Approach*: Order is being prepared AND a rider is assigned and en route to the shop.
  - *Live Delivery*: Order is picked up. Activates live telemetry map and direct driver chat banner.
  - *Completed*: Order delivered successfully.

## API Integrations
- **Resilient Offline/Server Sync**: All offline carts and failed Cloud Function calls intelligently fallback to the Dual Sync queue, gracefully pushing payload data to `/api/orders` when Firebase environments are locked or uncommunicative.

- **Supabase Backend**: Primary BaaS for auth and database operations.
  - Key Tables: `orders`, `rider_locations`, `profiles`, `shops`.
  - Real-time Subscriptions: Used extensively for live tracking `rider_locations` and instant `orders` status updates.
- **Leaflet / react-leaflet**: Core mapping engine handling all geospatial visualizations.

## Standardized Map Pin System Logic
- **Customer Location Pin**: Distinct Blue Pin with a pulsing live radar beacon (`userMapIcon`). Strictly enforced with `z-index: 2000` to guarantee it always renders visibly on top of all other elements.
- **Open Kitchens / Vendors**: Vibrant Orange Pin with storefront emblem and verified active badge (`createShopMapIcon(true)`).
- **Closed Kitchens**: Muted slate gray pin with offline status (`createShopMapIcon(false)`).
- **Live Couriers & Drivers**: Dedicated Indigo Pin with dynamic vehicle badges (bicycle, motorcycle, car, or scooter) and live proximity markers.
- **Coordinate Collision Safety**: Shops missing explicit GPS coordinates utilize a deterministic hashing and scattering algorithm (based on their shop ID) to distribute them gracefully and prevent marker stacking on a single default pixel.

Profile edits use a new explicit Firebase-authenticated LocalEats API POST followed by a same-account authenticated GET readback and precise field comparison; failures, mismatched users, HTML fallbacks, or unconfirmed writes are errors rather than a fabricated saved state. The Profile route bypasses the older optimistic upsert/offline retry helper; other legacy profile/onboarding paths remain outside this phase. Only user-editable profile fields can be submitted here; no client-supplied role. The original account API's actual durable persistence still needs device/backend verification; the Preview must not claim success where readback fails.

Customer Profile no longer exposes the Supabase/Firestore authentication diagnostic panel, invented recent-device gallery images, or unimplemented Bronze/Silver/Gold loyalty reward tiers. The original photo view remains, but fallback is rendered as a local initial rather than transmitting a customer's full name to the third-party avatar URL provider. Profile photo upload actions are intentionally not exposed until an authenticated, account-scoped upload API is validated; existing photo display and API-confirmed removal are retained. Phone number badges describe format validity, not possession verification; profile address text no longer promises active delivery, and location labels do not expose raw GPS coordinates. Status/success UI no longer calls untouched data verified or cloud-synchronized without readback.

This P1 branch is separate from draft Orders O2 PR #21 and must not be merged/released until all P1+O1/Map/Discover/Home/pickup/auth/checkout regressions, TypeScript and build pass plus authenticated mobile acceptance. No new SQL, database records, production domain/alias, order writes, Firebase rules, Merchant/Rider/Admin or backend deployment. Separate security follow-up required before any real profile-edit release: the existing server-side /api/profiles handler accepts role from client payload and its fallback memory store is not durable; other legacy CompleteProfile and profileService queues must be audited under an explicit backend-authority scope. Do not declare end-to-end profile persistence secure based solely on this UI candidate.

P1 follow-up hardening: the legacy asynchronous profile read now discards mismatched response-owner IDs, refuses to hydrate a profile after Firebase account changes, and starts from an empty same-account baseline instead of inheriting another account's cached email, address, phone or role. Missing-row fallback reads Firebase auth metadata for display only; it no longer auto-upserts a profile or trusts user-editable role metadata. This protects the scoped Customer Profile route without applying any SQL, deployment or existing record changes.

## Customer Profile P2 — 2026-11-03 (draft usability review; stacked on P1)
Profile P2 changes the Customer Profile page only; it is based on P1 branch `repair/customer-profile-p1-trust-01`, not merged to the O1 integration branch. It removes P1's unreachable camera/cropper/gallery/upload code rather than merely hiding it, preserving the display of an authenticated account's picture (local initial if absent) and an explicit API-confirmed removal action. The existing styling is kept; spacing, long email rendering and small-screen controls are improved. Name/phone inputs have real labels, autocomplete, linked inline errors, and focused invalid fields; phone formatting is described accurately as format validation, not ownership verification. Edits to one field do not force entry of unrelated phone/address/city information, and only modified profile fields are sent to the P1 authenticated, server-readback-checked endpoint. Saved-profile addresses and GPS pins are optional; the UI does not suggest that delivery is activated. Before Back/Sign Out discards unsaved edits, the user receives a native confirmation, and those actions are disabled during an active save. Offline state is explicit and disables writes. Recent success styling is suppressed when a new edit is pending.

P2 requires `tests/customer-profile-p2-usability.test.mjs` plus P1/O1/Map/Discover/Home/pickup/FCM/auth/checkout regression tests, TypeScript validation, full build and owner mobile review. P1 legacy server-side profile-role authorization, no-DB memory fallback and older onboarding/queued profile paths remain security blockers for any broader release. P2 creates no database records, migrations, API/backend changes, real order writes, Product/Production deployments, or other app updates. Do not merge P2 until P1 is approved and reviewed. No Customer Preview alias reassignment without owner acceptance.
